# Wire protocol

Definitions without `server` execute directly on the invoking backend unless `broadcast` or `/rcc target` overrides the destination. Local requests use the same validation, currency/command execution, and callback handling, but neither requests nor responses are sent over plugin messaging. Local execution needs no player carrier. Explicitly configured destinations and broadcast still use the bridge.

Channel: `rcc:bridge`. Every payload is at most 30,000 bytes. The first byte is version `3`; the second is type `1` (request), `2` (response), `3` (broadcast discovery), or `4` (server list). A 16-byte UUID follows. Strings use Java `DataOutputStream.writeUTF` encoding. Request fields are origin, target, unsigned-short command count, command strings, and a boolean currency-present flag. When true, six UTF strings follow: uppercase currency type, uppercase action, currency key, decimal amount (`BigDecimal` string form), player identifier, and optional player-name hint (empty if unavailable). Zero commands are valid only with a currency action. Response fields are origin, target, one-byte result code, and detail string. Discovery contains only the origin after the UUID. A server list contains the origin, unsigned-short server count, then server names. Older protocol versions are rejected. Upgrade Velocity and every RCC backend together.

Currency templates resolve at the origin, separately for each target. The destination validates the structured operation again, rejects unsupported provider types, and applies the currency action before the console command list. Account and profile loading may complete asynchronously; balance mutation and subsequent commands run on the server thread. A failed currency action skips the command list and returns command failure. In-progress request IDs are suppressed while asynchronous operations run, and completed results are cached for ten minutes to avoid repeating a transaction after duplicate delivery. This deduplication is in memory and does not survive server restart. Currency storage errors and ten-second timeouts are inconclusive about whether a transaction changed the account.

For broadcast, Velocity validates that discovery came from its claimed origin backend and returns all configured backend names. The origin correlates the list with its pending discovery and creates one independent request ID per unique destination. It resolves placeholders separately for each destination before sending requests. Server lists from arbitrary backend connections are never forwarded by the bridge. Each destination result triggers its matching callback list exactly once on the origin. Discovery failures trigger one error callback list. Discovery and each destination request have separate ten-second deadlines.

Result codes in order: success, command failure, routing failure, transport failure, timeout, invalid request. Velocity checks that the packet came from a backend, the request origin matches that backend, and a response comes from the outstanding request's target. Duplicate request IDs are not rerouted while pending. Destinations keep completed IDs for ten minutes and resend the stored result for a duplicate request.

The origin uses a ten-second timeout. Velocity also expires routes after ten seconds. A timeout is inconclusive: execution could have happened before a reply was lost. Paper's command dispatcher reports whether the command was accepted, which does not prove every command's intended effect. Fabric uses Brigadier's integer command result. All `runcmd` entries are attempted even after one reports failure. The aggregate succeeds only if all report success.
